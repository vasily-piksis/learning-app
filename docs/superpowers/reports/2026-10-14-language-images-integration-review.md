# Второе ревью: подготовка, регенерация и изображения

Дата: 14 октября 2026. Это проверка согласованности двух спецификаций и двух
планов, не отчёт о тестировании готовых функций. Проверены также текущие
jobs.retry/run_job, study.new_session/repeat, deletion.remove и CSP в main.py.
Платных запросов, изменения кода приложения и операций на сервере не было.

Первое ревью сохранено отдельно. Здесь — новые стыки и уточнения, появившиеся
после добавления подготовки, регенерации и изображений. P1 требует конкретного
контракта до соответствующей реализации; P2 — поведения и теста до приёмки.

## I01 — P1: лимит по Jobs не ограничивает число оплачиваемых попыток

Image spec «Генерация и контроль расходов», image plan Task 2. Текущий
POST /jobs/{id}/retry повторно ставит ту же строку Job в queued. Десять Jobs
с неограниченными ручными retries могут вызвать больше десяти image requests.
Отмена/перезапуск после отправки не означает отсутствие списания.

**Уточнение:** считать резервируемые попытки провайдера, не строки Job.
ImageRequest связывает Job и attempt_no, имеет состояния reserved/sent/
succeeded/failed/unknown. Резерв квоты атомарен непосредственно перед отправкой;
все исходы расходуют слот, новая ручная попытка расходует новый. SDK retries=0,
общий retry для generate_image запрещён: только явный image-specific retry
с новым ключом и указанием платности. Временная зона лимита задаётся оператором
и показывается пользователю. Конфигурация не проверяется пробной генерацией.

**Тесты:** 10 попыток через один/несколько Jobs исчерпывают limit; concurrent
11-я не обращается к API; timeout/crash/cancel не возвращает слот; повтор
одного request key не создаёт новую попытку. Граница суток/часового пояса.

## I02 — P1: новый повтор может потерять картинки старого занятия

Core plan Task 3 копирует содержимое snapshot с новым перемешиванием, image
plan добавляет отдельную SessionImage. Нынешний repeat получает только snapshot.
После замены/удаления Card новый повтор не сможет восстановить изображения
из текущей библиотеки. Копировать ссылки на старый session URL тоже нельзя.

**Уточнение:** при repeat создавать новые SessionImage из прежних SessionImage
в той же транзакции, сохраняя asset/alt/slot. URL выдачи относится к новому
занятию/позиции. Legacy snapshots без SessionImage получают пустой набор.
Cleanup учитывает и старое, и новое занятие. Материалы Card не перечитываются.

**Тесты:** заменить/удалить Card→repeat старой ошибки→старые байты/alt видны;
удалить исходную историю — повтор сохраняет файл; удалить последнюю — файл
очищается. Другая пользовательская история не получает доступ к новому URL.

## I03 — P1: «Применить новый текст» и «Убрать картинку» не имеют общего контракта

Core plan Task 6 apply-regeneration принимает только candidate. Image plan
Task 3 обещает keep/remove и единое сохранение. Два независимых PATCH сначала
увеличат version, затем конфликтуют; частичное применение оставит неверную
иллюстрацию либо изменит текст без выбранного удаления изображения.

**Уточнение:** в image-этапе extend apply-regeneration телом image_updates,
использовать тот же валидатор/транзакцию, что CardEdit. None оставляет связи,
asset_id=null явно удаляет slot, кандидат заменяет. Текст+связи+version+метка
применения сохраняются атомарно. До этого основной текстовый этап работает
без изображений и не требует зависимости от будущей миграции.

**Тесты:** keep/remove/replace с новым текстом увеличивают version ровно раз;
ошибка кандидата изображения не меняет текст; конфликт не меняет ни один slot;
старый снимок сохраняет изображения и текст. Готовый вопрос не превращается в draft.

## I04 — P1: кандидаты и очистка файлов не описаны полностью

Image spec обещает возвращение к draft, но image plan содержит создание и
DELETE, не содержит GET списка/предпросмотра/устаревших кандидатов. Отказ
от JobImage сам по себе не удалит файл: ImageAsset всё ещё помечен draft и
ссылается на живую Card. Проверка последней ссылки и unlink без блокировки
также допускают гонку с созданием новой ссылки.

**Уточнение:** определить список/preview для собственных draft, состояния
draft→ready/obsolete/discarded→deleting→deleted. Obsolete означает конфликт
версии, а не потерю файла: можно посмотреть, удалить или явно перепривязать
к текущей версии бесплатно. При discard убрать все draft/Job references.
Cleanup транзакционно помечает deleting после проверки ссылок; новые attach
не принимают deleting/discarded. Failed unlink сохраняет deleting для retry.
Временный файл и намерение записи учитываются; сбой между файлом/БД убирается
при восстановлении. UI использует авторизованный same-origin preview, без
blob URLs, которые не разрешены нынешним CSP.

**Тесты:** закрыть/вернуться/старая версия, отказ после generation, зависшая
запись, unlink error, concurrent attach/cleanup; после discard нет логически
«живого» draft. Upload preview проходит с текущим CSP, чужой draft не виден.

## I05 — P1: защита от двойного вызова обычной подготовки остаётся только обещанием

Core spec показывает existing Job, но GenerateBody не имеет request key;
дедупликация Card после ответа модели не предотвращает два платных вызова.
Двойной клик, потерянный HTTP response и повтор из другой вкладки создадут
несколько одинаковых Jobs. Regenerate после получения непринятого кандидата
также не должен незаметно оплачивать новый вариант.

**Уточнение:** новая UI-подготовка всегда отправляет стабильный idempotency_key;
сервер сравнивает канонический request fingerprint и хранит связь с Job.
То же касается prepare-options/regenerate. Тождественный активный scope
(материалы/версии, тема/тип/цель/count) повторно использует задачу атомарно.
Изменённый payload с тем же key — 409. Непринятый кандидат сначала показывается;
«Другой вариант» — отдельное явное действие с новым key. Другая приватная
задача не выдаётся по Job ID чужому пользователю: показывается busy без содержимого.

**Тесты:** параллельные одинаковые запросы/response lost — один Job/один вызов;
изменённые материалы/count не ошибочно дедуплицируются; завершённая задача
возвращается по тому же key без нового вызова. Legacy request без key не
обещает терминальное повторение, но имеет защиту активного fingerprint.

## I06 — P2: default mixed и неподходящий тип могут вести в круг подготовки

«Все доступные типы» неоднозначно для тем A={choice,written}, B={choice}.
Сервер требует готовность каждой пары, но default mixed не определён.
unsupported_types возвращается в succeeded Job, тогда как availability
имеет только count/job status. «Окончаний нет» может снова предлагать оплатить
тот же заведомо неподходящий материал, не показывая сохранённую причину.

**Уточнение:** default mixed — общий готовый набор выбранных тем; пользователь
видит список и может явно выбрать дополнительные типы с показом missing_pairs.
Если общий набор пуст, показать подготовку/изменение выбора. В availability
сохранить last_outcome с method, source fingerprint и reason: «Не получилось
по выбранным материалам», без объявления темы навсегда неподходящей. Новый
материал/контекст делает оценку устаревшей. Повтор всегда явный.
ready вместе с drafts не блокируется добавочной подготовкой.

**Тесты:** A/B default choice, явный written требует B; пустое пересечение;
частичный успех, unsupported со старым/новым набором документов; готовые
10 вопросов доступны, пока ещё 5 готовятся/проверяются.

## I07 — P1: иллюстрация и материал визуального задания — разные роли

Image spec исключает OCR/новые факты из изображений. Regenerate получает
только card/sources. Если пользователь вручную создал «Что изображено?» с
картинкой кошки, модель без картинки может заменить вопрос/ответ на собаку.
Проверка пар/текста сама по себе не выявит это. Изображение может также
содержать часть ответа, которую нельзя пропускать при объяснении.

**Первоначально требовался выбор:** только иллюстрации в первой версии или также
задания, где картинка — учебный материал. Во втором варианте нужны typed
asset-source references, версия картинки в request fingerprint, авторизованное
чтение исходных байтов для vision-входа regenerate/explain, проверка источников
и запрет silent text-only fallback. Это не вызов генератора картинок и не
оценка устного/визуального ответа моделью во время занятия.

**Тесты после выбора:** изменённая картинка/версия не даёт stale apply;
regenerate/explain получают именно изображение нужного вопроса/старого снимка,
а не новую картинку Card; неподдерживаемая vision-модель даёт понятную ошибку,
оригинал сохраняется. Ни один запрос не отправляет лишние чужие изображения.

**Ответ пользователя:** «Пока только иллюстрации». I07 закрыт без расширения
AI-входов: самостоятельные задания по прикреплённой картинке не добавляются,
вопрос/ответ определяются текстом и источниками, regenerate/explain не получают
картинки. При замене текста сохранённая иллюстрация проверяется в preview
пользователем. Тесты вместо vision-сценария проверяют отсутствие image inputs,
ясную подсказку роли иллюстрации и атомарные keep/remove/replace.

## I08 — P2: в допустимых ответах пропуска могут остаться «мёртвые» варианты

accepted_answers поля и accepted_combinations — два представления правильности.
Сейчас проверяется только, что значения комбинации есть в accepted_answers.
Обратное не проверяется: значение может быть указано допустимым, но не входить
ни в одно полное сочетание и никогда не приниматься.

**Уточнение:** после той же нормализации accepted_answers каждого поля должен
в точности совпадать с проекцией этого поля из accepted_combinations. В редакторе
они выводятся/обновляются из комбинаций; сервер отвергает противоречие.
Запретить дубли сочетаний после нормализации, не генерировать декартово
произведение автоматически. Ending с одним полем подчиняется тому же правилу.

**Тесты:** лишнее/непредставленное значение=422; все заявленные допустимые
значения достижимы; NFC/case не создают скрытых дублей; I+are остаётся неверным.

## I09 — P2: бесплатный этап загрузки не имеет своего порядка выпуска

Image plan утверждает независимый выпуск upload, но UI существует лишь в Task 3
после Images API Task 2. «Первое подключение проверяет model» также не определяет,
не создаётся ли при включении платная тестовая картинка.

**Уточнение:** порядок: storage/upload backend → upload UI и QA (отдельный
выпуск возможен) → выключенный по умолчанию image-generation backend → платная
кнопка и QA. Model/config проверяются без generation; фактическая доступность
проверяется первым явным платным Job. Никакой пробной картинки при старте,
открытии профиля или переключении флага. Обычный CI использует подмену API.

**Тесты:** приложение/upload стартуют без image model/key/access; включение
флага и открытие формы не вызывают API; первый paid click делает ровно один
запрос. Upload-only browser journey не зависит от image provider.

## I10 — P1: повтор применения регенерации с другим кандидатом не определён

Core plan обещает повтор apply без второго изменения, но единственная метка —
applied_version. Изменённый после первого Save кандидат может получить
«уже применено» вместо 409. Concurrent Apply/Discard тоже не определяет,
кто выиграл. После чужого редактирования нельзя выдавать новую текущую Card
как результат старого применения.

**Уточнение:** сохранять applied_fingerprint и компактный applied_result вместе
с атомарным update. Тот же apply payload возвращает сохранённый результат,
другой — 409. Apply/Discard имеют взаимоисключающие состояния; lock-транзакция
решает гонку, проигравшая операция не меняет Card. Не применять discard как
откат уже применённого текста. Hash включает решения по изображениям, когда
image-этап установлен.

**Тесты:** тот же apply после сетевого сбоя возвращает прежний результат;
изменённый candidate/image_updates=409; чужая более свежая Card сохраняется;
parallel Apply/Discard — только один переход; deleted Card никогда не восстанавливается.

## Результат

Правила I01–I06/I08–I10 и соответствующие тесты внесены в оба плана/спецификации.
I07 закрыт явным ответом пользователя, не предположением. Ручная загрузка
получила самостоятельный порядок выпуска до AI-генерации. Это согласованность
документов, не утверждение, что будущая реализация уже прошла тесты.
Код приложения, семейный сервер, .env и данные не менялись.
