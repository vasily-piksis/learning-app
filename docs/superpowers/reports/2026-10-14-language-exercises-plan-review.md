# Проверка плана языковых заданий: адвокат дьявола

Дата: 14 октября 2026. Проверены спецификация и план от этой даты, а также
нынешние ai.py, jobs.py, quiz.py, study.py, library.py, db.py и deploy.py.
Это ревью проекта решений, не проверка готовой реализации. Внешние платные
запросы и операции на сервере не выполнялись.

После ревью пользователь уточнил: явная подготовка до занятия, готовность
по каждой теме/способу, только исходный язык содержимого, регенерация одного
вопроса и изображения отдельным этапом. Основной план/спецификация обновлены
с этими решениями и предложенными исправлениями комбинаций, единого решения,
сохранённой оценки и отката. Ниже сохранён исходный разбор; ссылки на номера
строк относятся к версии до этих уточнений. Три выбора в конце отчёта больше
не являются актуальными вопросами: перевода содержимого нет, несколько
пропусков проверяются комбинациями, подготовка вариантов только явная.

**Вывод:** направление подходит, но перед реализацией нужно закрыть описанные
ниже правила. Основные риски: формально правильная проверка может давать
неправильную учебную оценку; история может переоцениваться новым алгоритмом;
автоматический возврат Docker-образа не обеспечивает откат миграции.

Обозначения: P1 — закрыть до реализации соответствующего этапа; P2 — зафиксировать
поведение и тест до приёмки. Все решения ниже — предложения для уточнения плана,
не незаметная замена уже согласованного объёма. Озвучка по-прежнему исключена.

## R01 — P1: переводы и грамматика конфликтуют с правилом «только из источника»

**Основание:** spec:53,60–67,117–118; ai.py:27–34,154.
В источнике есть только английское слово, а упражнение обещает перевод на
польский: откуда берётся допустимый ответ? Сейчас одно language описывает
вопрос, ответ и варианты. target_language переводит весь результат, что может
уничтожить смысл упражнения на литовское окончание.

**Предложение:** явно разделить учебные факты и разрешённые языковые операции.
Для content факты/ответы подтверждаются источником. Для language можно
применять грамматику к словам источника, сохраняя контекст и ссылку; родитель
проверяет результат. Для перевода отдельно задавать язык ответа, не подменяя
язык исходного слова. Перевод всего упражнения с окончаниями запретить в
первой версии с понятным объяснением; перевод интерфейса этому не мешает.
Если не хотим расширять языковые поля, честный более узкий вариант — переводы
только из уже двуязычных материалов. Эти варианты надо выбрать явно.

**Проверки (Task 2/4/6):** en→pl сохраняет английское слово, польские допустимые
ответы и источник; литовское окончание не превращается в русское упражнение;
исторические факты из общих знаний модели по-прежнему не добавляются.

## R02 — P1: несколько пропусков могут зависеть друг от друга

**Основание:** spec:89–93, plan Task 1.
Пример `___ ___ happy`: первое поле допускает I/We, второе am/are.
Независимая проверка признает `I are happy` правильным, хотя допустимы только
сочетания I+am и We+are.

**Предложение:** добавить закрытый список допустимых комбинаций для всего
упражнения. Поля показывают локальные ошибки, а итог проверяется по допустимой
комбинации. Если все значения по отдельности допустимы, но сочетание нет,
сообщение явно объясняет несовместимость. Более простой вариант первой версии —
один пропуск в задании; он сокращает уже предложенный объём и требует решения.

**Проверки (Task 1/3/5):** I+am и We+are верны, I+are неверен; частичная
обратная связь не показывает противоречивое «всё верно, но ответ неверный»;
комбинации скрыты до проверки. В генерации представлять их списком типизированных
элементов, а не произвольным объектом с динамическими ключами.

## R03 — P1: два независимых источника правильного решения

**Основание:** spec:84,145; plan Task 4 ExerciseEditor/ExerciseSolution.
Card.answer и accepted_answers/pairs/accepted_orders редактируются независимо.
Можно получить answer="1920", accepted_answers=["1918"]: проверка принимает
одну дату, флеш-карта и объяснение показывают другую.

**Предложение:** для новых типов exercise — единственный источник проверяемого
решения. Отображаемое решение формируется из него детерминированно. Если нужно
человеческое пояснение, оно отдельное и не определяет правильность. Передать
в explain также структурированное решение. Для старого choice сохранить
нынешний контракт, не переписывая старые данные.

**Проверки (Task 1/2/4/5):** изменение допустимого ответа меняет решение
флеш-карты; нельзя сохранить несовместимый независимый ответ; пояснение не
заменяет критерий проверки. История использует сохранённую версию упражнения.

## R04 — P1: неизменная история сейчас зависит от будущего проверяющего кода

**Основание:** spec:165–173; plan Task 3, интерфейс feedback/Review.
Attempt.correct сохраняется, но parts предлагается пересчитывать при чтении.
После изменения правил нормализации старая попытка может остаться «неверной»,
а все её поля станут «верными». Один snapshot_version фиксирует форму данных,
но сам по себе не фиксирует алгоритм.

**Предложение:** сохранять итог и обратную связь parts в момент ответа,
вместе с grading_version. Можно использовать служебный объект внутри
существующего Attempt.value, без новой таблицы; при сравнении идемпотентности
сравнивать только пользовательскую часть. История читает сохранённый результат,
не пересчитывает его. Старые Attempt без метаданных продолжают показывать
сохранённый correct и прежние ответы.

**Проверки (Task 3):** новая версия grader не меняет old correct/parts;
одинаковый повтор запроса возвращает сохранённый feedback; legacy attempts
читаются без вызова нового grader. Уточнить правила преобразования value
до реализации, чтобы API/idempotency/history не использовали разные формы.

## R05 — P1: запуск теста может неожиданно вызвать оплачиваемую генерацию

**Основание:** spec:35,75–76; quiz.py:26–67; study.start.
У старой флеш-карты нет вариантов. Выбор «Выбор ответа» или mixed запускает
prepare_quiz, который обращается к модели. Это противоречит обещанию отсутствия
скрытых списаний, хотя такое поведение уже есть в приложении.

**Предложение:** выбор в селекторе ничего не генерирует. До «Начать» показывать,
что часть вариантов надо подготовить один раз; действие называется
«Подготовить варианты и начать». Отказ сохраняет флеш-карты и не вызывает AI.
Сервер принимает явный флаг разрешения подготовки для новых запусков;
продумать совместимость старого клиента. Счётчики различают готовые вопросы
и вопросы, которым нужна подготовка, не выдавая их решения.

**Проверки (Task 2/3/5/6):** только written/gap не вызывают prepare_quiz;
неподготовленный choice без явного разрешения не вызывает AI; mixed заранее
показывает необходимость подготовки; после успешной подготовки повторный
запуск обходится без модели. Старый активный quiz продолжает работать.

## R06 — P1: конечный список ответов не гарантирует признание всех верных ответов

**Основание:** spec:86–88,105–118.
«Ответь своими словами» несовместимо с точным сравнением. Даже для короткого
ответа возможны синонимы, числовая/словесная дата, сокращение. У сборки
предложения может быть больше одного грамматически допустимого порядка.
У упражнения на окончание фиксированная основа может не подходить, если
требуемая форма также меняет основу.

**Предложение:** письменный ответ — явно ограниченное слово/дата/короткая
форма, с контекстом и редактируемыми вариантами; не обещать оценку свободной
речи. У порядка — несколько перечисленных вариантов или формулировка
«восстанови предложение из материала». Для ending ограничить генерацию
формами, где показанная основа действительно остаётся неизменной; нулевое
окончание уже сознательно исключено. Не исправлять эти ограничения нечётким
сравнением, которое может простить как раз проверяемое окончание/букву.

**Проверки (Task 1/2/4/6):** два контекстно допустимых перевода принимаются;
отдельный неверный перевод отклоняется; варианты даты заданные, а не угаданные;
второй разрешённый порядок принимается; редактирование вариантов доступно.
Проверка родителем — часть процесса, не гарантия автоматической семантики.

## R07 — P2: выбранная тема может вообще не попасть в занятие

**Основание:** spec:36–39; plan Task 3 StartBody/Topic.question_type_counts.
В теме A есть written, в B — только choice. Выбраны обе и способ written.
Сумма счётчиков ненулевая, но занятие названо A+B и проверяет только A.

**Предложение:** показать вклад каждой выбранной темы для выбранного метода.
Если тема даёт ноль, предложить убрать её/выбрать другой метод до запуска;
не пропускать её молча. Зафиксировать серверную политику: отклонение такого
запуска или явное подтверждение исключения. Учитывать тот же лимит 300 и
обновление/удаление вопросов между загрузкой счётчиков и нажатием «Начать».

**Проверки (Task 3/5/6):** A+B и written не выдаёт тихое занятие только по A;
удаление вопроса перед start даёт понятный результат, а не призрачный счётчик;
не более 300 фактически подходящих карточек; пустой mixed не запускается.

## R08 — P2: повторение закрепляет расположение, а не знание

**Основание:** spec:155–156,168; plan Task 3 repeat.
Нынешний repeat копирует снимки. Для matching/ordering это сохранит те же
ID и перестановку. Ребёнок может запомнить позиции, а не соответствия.
Случайная первая перестановка также может уже быть правильным ответом.

**Предложение:** внутри одного занятия порядок стабилен при reload. При
новом/повторном занятии переиспользовать содержание и критерии старого снимка,
но заново создавать ID/перестановку. Не принимать в генерации бессодержательное
ordering из одинаковых токенов; учитывать допустимые порядки при проверке,
что исходный банк не выдан уже как готовое решение.

**Проверки (Task 1/3/6):** reload сохраняет раскладку, repeat создаёт новую,
старое занятие не меняется, AI не вызывается, одинаковые слова не теряются.
Проверять свойства перестановки, не надеяться на случайный результат теста.

## R09 — P1: тесты JSON-контракта и размер генерации недостаточно конкретны

**Основание:** plan Task 2, тесты адаптера; ai.py:50–99,171; spec:86–107,125.
Подменённый responses.parse способен принять любую схему и вернуть готовый
Pydantic-объект. Такой тест не докажет, что реальный API примет вложенные
варианты exercise. Максимум 30 сложных вопросов с несколькими альтернативными
порядками резко увеличивает ответ относительно прежних коротких quiz.
Текущий предел генерации — 18 000 output tokens, не гарантированный бюджет
для любых комбинаций новых верхних границ.

**Предложение:** добавить офлайн-проверку фактической сериализованной SDK-схемы:
root object, замкнутые объекты, required-поля, nullable-опциональность,
поддерживаемые вложенные anyOf, отсутствие произвольных ключей и неподдерживаемых
конструкций. Разделить модельную схему и HTTP-схему ответа (gap_answers может
быть словарём в HTTP, но не свободным словарём в результате модели).
Определить реалистичные размеры генерации/длину упражнений и поведение при
incomplete: понятное предложение уменьшить объём, без скрытого увеличения
лимита/дробления на дополнительные платные запросы. Без реального вызова
это проверка контракта, не обещание фактической доступности модели.

**Проверки (Task 2/6):** анализ схемы после преобразования установленным SDK,
не только model_json_schema; неправильная схема падает локально; неполный
ответ не сохраняется как успешный; refusal/429/5xx и бюджет retry=3 сохранены.
Ссылки на источники не доказывают правильность самого учебного содержания.

Источник API-ограничений: [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas).
Вывод о недостаточности mock-теста — сопоставление этих требований с текущим
кодом SDK `_ensure_strict_json_schema` и тестовым подменённым транспортом.

## R10 — P1: откат Docker-образа не вернёт базу на предыдущую миграцию

**Основание:** plan Task 6; db.py:26–30; deploy.py:93–118.
Новая версия мигрирует при старте, затем может не пройти healthcheck. Скрипт
запускает старый образ с уже новой SQLite. Старый Alembic может не знать 0006,
поэтому «старый образ запущен» не означает восстановление приложения.
Восстановление предобновлённого backup после новых ответов ребёнка потеряет их.

**Предложение:** перед выпуском этого изменения добавить конкретный регламент
миграции/отката и проверить его на отдельной копии. Сборка проходит заранее;
запись в семейные данные приостанавливается до финального холодного backup,
миграции и healthcheck. В случае неудачи сохраняется отдельная копия состояния
после сбоя, затем восстанавливаются проверенный том и старый образ. Приложение
открывается после проверки согласованности схемы и образа. Обычный fallback
скрипта не считать достаточным для выпуска со сменой схемы.

**Проверки (Task 6):** реальный Docker на отдельном QA-томе: migration успешна,
затем запуск падает; восстановление image+volume возвращает healthy, исходные
таблицы/историю/файлы, .env неизменён. Семейный том не использовать в таком тесте.

## R11 — P2: обещание скрытых решений требует уточнения границы

**Основание:** spec:151–154; текущие GET /cards и экран Questions.
Библиотека общая и позволяет любому вошедшему читать/редактировать вопросы с
ответами. Нельзя одновременно обещать, что ребёнок вообще не может узнать
решение до ответа: он может открыть сам вопрос в библиотеке.

**Предложение:** сформулировать гарантию точно: API занятия/ошибки не раскрывают
решение до проверки/раскрытия, доступ анонимных пользователей запрещён,
история приватна. Просмотр решения в общей библиотеке — существующая учебная
возможность. Роли «родитель/ребёнок» и режим экзамена сейчас не добавлять.

**Проверки (Task 3/6):** публичные JSON занятия не содержат решений; вопросы
библиотеки доступны только после входа; чужая история недоступна. Не писать
тест, обещающий изоляцию, которой по архитектуре общей библиотеки нет.

## R12 — P2: потеря незавершённого ввода и непонятные показатели истории

**Основание:** plan Task 3/5; текущий History.tsx показывает только mode.
Сохранение попытки после «Проверить» не означает сохранение набранного, но
неотправленного ответа при reload. Также история под названием «Тест» не
объясняет, были это пары, окончания или смешанная практика. В matching 7/8
верных пар всё ещё дают одну неверную карточку: это согласованное правило,
но ребёнок должен понимать, что именно посчитано.

**Предложение:** явно ограничить сохранение отправленными ответами; autosave
неотправленного ввода не добавлять в первую версию. Сохранённый HTTP-ответ при
потере сети доступен из истории; повтор с тем же ключом не создаёт попытку.
В истории добавить эффективные типы/количества из снимков, без выдачи скрытых
решений активного занятия. Показать общий результат по заданиям и локальный
результат по частям, не смешивая две шкалы. Добавить History.tsx в карту файлов.

**Проверки (Task 3/5/6):** submitted сохраняется после reload и сетевого сбоя;
unsubmitted не объявляется сохранённым; карточка истории показывает вид
практики; 7/8 пар → 0/1 задания и 7/8 частей с понятными подписями.

## Что нужно выбрать до обновления спецификации

1. Языковые операции: разрешаем грамматику/перевод для слов источника с
   отдельным языком ответа, либо ограничиваемся явно данными двуязычными примерами?
2. Пропуски: поддерживаем совместимые комбинации нескольких полей, либо
   первая версия содержит один пропуск на задание?
3. Старые флеш-карты: явно разрешаем одноразовую подготовку вариантов перед
   тестом, либо запускаем выбор ответа только для уже подготовленных карточек?

Остальные замечания можно закрыть уточнением контрактов и тестов, без
добавления аудио, новых сервисов, ролей пользователей или других подсистем.
